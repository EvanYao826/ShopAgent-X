### 1.2 请求链路

**普通对话流程：**
```
App 发送消息 → Java ChatController.sendMessage()
  → 调用 Python /api/chat/stream (SSE 流式)
  → RouterAgent 意图分类 → 分发到子 Agent
  → 子 Agent 处理（可能调用 Tool）
  → SSE 逐 token 返回 → Java 透传 → App 逐字渲染
```

**商品推荐流程：**
```
用户: "推荐一款洗面奶"
  → RouterAgent: 意图=shopping → ShoppingAgent
  → ShoppingAgent:
    1. 读取会话记忆
    2. FAISS 向量检索相关商品知识
    3. MySQL 四级搜索流水线（排除词→关键词→精确匹配→泛词展开）
    4. LLM 生成推荐话术
    5. 构建商品卡片 JSON
  → SSE 返回: routed → token(逐字) → product_cards → end
```

### 1.3 Agent 协作拓扑

```
RouterAgent（中央路由，8 类意图，88.9% 准确率）
  │
  ├── ShoppingAgent      → 商品推荐 / 购物车管理 / 反选排除
  ├── KnowledgeQAAgent   → L1 直答 / L2 检索 / L3 编排
  ├── ChitChatAgent      → 闲聊（带会话记忆）
  ├── ReasoningAgent     → 复杂推理
  └── AdminCopilotAgent  → 运营分析 / 知识巡检
        ├── OpsAgent
        └── InspectionAgent
```

### 7.1 RouterAgent — 意图分类

**输入：** 用户消息文本
**输出：** 意图类别 + 复杂度判断

**8 类意图：**

| 意图 | 触发示例 | 分发目标 | 复杂度 |
|------|---------|---------|--------|

**复杂度路由：**
- 简单 → RouterAgent 直接分发到子 Agent，~2s
- 中等 → 子 Agent + Tool 调用，~4s
- 复杂 → Orchestrator → Planner → Executor 完整编排，~8s

### 7.2 ShoppingAgent — 购物导购

核心 Agent，1700+ 行代码，负责：

**RAG 链路（7 步）：**
1. 意图检测 → 识别对比/购物车/普通推荐
2. 会话记忆读取 → 获取对话历史
3. FAISS 向量检索 → 语义匹配商品知识（k=8, 阈值 0.6）
4. MySQL 四级搜索流水线：
   - Step 1: LLM 提取排除词（"不要优衣库" → ["优衣库"]）
   - Step 2: LLM + 正则提取搜索关键词（双保险）
   - Step 3: 三级优先级匹配（精确 > 泛词展开 > 拆字匹配）
   - Step 4: SQL 参数化搜索 + 品类过滤 + 排除词过滤
5. 结果合并去重 + 加权排序（评分 60% + 销量 40%）
6. LLM 生成推荐话术
7. 构建商品卡片 JSON + 推荐日志记录

**购物车管理：**
- 自然语言指令识别：加购/删除/批量删除/查看/清空
- 会话级购物车缓存（30s TTL）
- 确认卡片交互（删除前确认）

### 7.3 KnowledgeQAAgent — 三级知识问答

| 级别 | 复杂度 | 处理方式 | 示例 |
|------|--------|---------|------|
| L1 | 简单 | 直接从商品字段回答 | "这款手机多少钱" |
| L2 | 中等 | 向量检索 + LLM 生成 | "敏感肌适合什么面膜" |
| L3 | 复杂 | Orchestrator 完整编排 | 多步推理、多文档综合 |

### 7.4 五层编排框架

```
Orchestrator.run()
  ├── GuardrailsPolicy  → 输入校验（长度/安全/格式）
  ├── Planner.plan()    → 生成执行步骤列表
  ├── Executor.execute() → 循环执行每个 step
  │     ├── step_type: tool_call → 调用 ToolRegistry
  │     ├── step_type: llm_call  → 调用 LLM
  │     └── step_type: condition → 条件分支
  ├── EventBus.publish() → 事件监控
  └── RetryPolicy       → 失败重试（max_retries=3）
```

## 8. 关键问题解决方案

### 8.1 RAG 检索精度优化

**问题：** 用户说"推荐跑鞋"，拆字逻辑把"跑"和"鞋"单独匹配，导致篮球鞋也混入结果。

**解决方案：** 四级搜索流水线

```
用户问题
  → Step 1: LLM 提取排除词（"不要优衣库" → ["优衣库"]）
  → Step 2: LLM + 正则提取搜索关键词（双保险）
  → Step 3: 三级优先级匹配
       精确匹配: "跑鞋" → 只匹配"跑步鞋"，不展开
       泛词展开: "鞋子" → ["篮球鞋","跑步鞋","徒步鞋","运动鞋"]
       拆字匹配: 中文单字拆分模糊搜索
  → Step 4: SQL 参数化搜索 + 品类过滤 + 排除词过滤
  → Step 5: 后处理 → 去重 + 状态过滤 + 加权排序（评分60% + 销量40%）
```

**关键代码：** `workflows/shopping_agent.py` — `_search_products()`

### 8.2 防幻觉机制

**问题：** LLM 可能编造不存在的商品、价格、评分等数据。

**三层防幻觉：**

| 层级 | 机制 | 说明 |
|------|------|------|
| Prompt 约束 | LLM Prompt 明确指令 | "不要编造价格/评分/销量数据" |
| 输出校验 | validateProductCards() | 用 product_id 查数据库，比对价格/标题/状态，不一致则覆盖 |
| 参数化查询 | SQL 注入修复 | CASE 表达式从 f-string 改为参数化查询 |

**关键代码：**
- `service/impl/ChatServiceImpl.java` — `validateProductCards()`
- `workflows/shopping_agent.py` — `_validate_llm_prices()`

### 8.3 多轮上下文记忆

**问题：** 用户说"推荐跑鞋"后说"要轻量的"，Agent 需要理解"轻量的"指的是上一轮的跑鞋。

**解决方案：**
- 会话记忆读取：每次请求前读取 `conversation_context` 表
- 记忆写入：RouterAgent 统一入口写入（避免重复写入）
- 上下文感知：LLM Prompt 注入对话历史，理解"那个"、"它"等指代

### 8.4 反选排除

**问题：** 用户说"推荐防晒霜，但不要含酒精的"，需要在检索阶段排除含酒精商品。

**解决方案：**
- LLM 提取排除关键词 → `["酒精"]`
- SQL 搜索时增加排除条件：`WHERE tags NOT LIKE '%酒精%'`
- 后处理阶段再次过滤

### 8.5 语音输入

**链路：**
```
Android MediaRecorder 录音 (MPEG_4/AAC, 16kHz)
  → 上传音频文件 (Multipart)
  → Java 透传 → Python /api/voice/recognize
  → 豆包多模态模型 ASR（非独立 ASR 服务）
  → 返回文字 → 填入输入框 → 用户确认后发送
```

### 8.6 拍照识图

**链路：**
```
Android 拍照/选图
  → 上传图片 (Multipart)
  → Java 透传 → Python /api/recognize-image
  → 豆包 Vision API 理解图片语义
  → 返回描述（如"一双白色Nike运动鞋"）
  → 作为搜索词走 ShoppingAgent 检索链路
  → 返回推荐商品 + 商品卡片
```

### 8.7 对话式购物车管理

**问题：** 用户通过自然语言控制购物车，Agent 需要精准识别多种操作意图。

**支持指令：**

| 操作 | 示例 |
|------|------|
| 加购 | "把这个加到购物车" |
| 泛化加购 | "添加购物车"（显示选择卡片） |
| 删除 | "删除第二个商品" |
| 批量删除 | "删除前两个" / "清空购物车" |
| 查看 | "看看我的购物车" |

**实现：** 正则意图识别 + 商品 ID 解析 + 确认卡片交互 + 30s 会话缓存

### 8.8 IDOR 安全漏洞修复

**问题：** 部分接口的 userId 由客户端传入，存在越权风险。

**解决方案：** Java 端统一从 JWT Token 获取用户身份：
```java
SecurityContextHolder.getContext().getAuthentication().getName()
```

## 10. 开发过程中遇到的问题与解决方案

### 10.1 LLM 输出截断问题

**问题：** 使用 qwen-plus 模型时，即使在 Prompt 中指定了回复长度限制，模型仍然经常忽略指令，生成超长回复导致 token 浪费和响应延迟。

**解决方案：** 在代码层面实现双重截断保障：
- **Prompt 级：** 在 System Prompt 中明确指令"控制在 X 字以内"
- **Token 级：** 配置 `max_tokens` 参数硬性限制输出长度
- **代码级：** 生成完成后对输出文本做字符数截断，超长部分直接裁剪并补充省略号

三层保障确保无论模型是否遵守指令，最终输出都在可控范围内。

### 10.2 工具注册中心线程池问题

**问题：** `tools/registry.py` 中的 `invoke_tool()` 方法每次调用都创建一个新的 `ThreadPoolExecutor(max_workers=1)`，高频调用时线程创建/销毁开销大，且无法复用线程。

**解决方案：** 改为共享线程池模式：
- 在 ToolRegistry 初始化时创建一个全局共享的 `ThreadPoolExecutor(max_workers=10)`
- 所有 `invoke_tool()` 调用复用同一个线程池
- 线程池生命周期与应用一致，避免反复创建销毁

### 10.3 工具执行跟踪内存泄漏

**问题：** `tools/execution.py` 中的 `ToolExecutionTracker` 只记录不清理，执行记录无限增长，长时间运行后内存持续膨胀。

**解决方案：** 引入容量上限 + TTL 自动淘汰：
- 设置最大容量 1000 条记录
- 每条记录设置 TTL 3600 秒（1 小时）
- 超过容量或 TTL 过期的记录自动淘汰
- 采用 LRU 策略优先淘汰最久未访问的记录

### 10.4 记忆写入重复

**问题：** `base_agent.py` 和 `memory_agent.py` 两处都在写入会话记忆，导致同一条对话被重复记录，记忆表数据冗余且可能干扰上下文检索。

**解决方案：** 统一记忆写入入口：
- 记忆写入统一收敛到 RouterAgent（`router_agent.py`），作为唯一的记忆写入点
- 子 Agent（ShoppingAgent、ChitChatAgent 等）不再自行写入记忆
- 通过 `memory_write` 工具统一管理，避免重复写入

### 10.5 流式模式未读取会话记忆

**问题：** `chitchat_agent.py` 的 `chat_stream()` 方法没有读取会话记忆，导致流式模式下 Agent 无法记住之前的对话内容，多轮对话体验断裂。

**解决方案：** 在流式方法开头补充记忆读取逻辑：
- 调用 `memory_read` 工具获取当前会话的历史记忆
- 将记忆内容注入 LLM Prompt 的上下文部分
- 确保流式和非流式两种模式的记忆一致性

### 10.6 Agent 绕过 ToolRegistry 直接实例化工具

**问题：** 部分 Agent（如 `retrieval_agent.py`）直接实例化工具类，绕过了 ToolRegistry 的统一管理，导致工具调用没有执行跟踪、超时控制和重试机制。

**解决方案：** 统一通过 ToolRegistry 调用：
- 所有工具调用必须通过 `tool_registry.invoke_tool("tool_name", params, run_id)`
- 禁止直接实例化工具类
- 在代码审查中加入此规范检查

### 10.7 IDOR 安全漏洞

**问题：** `ChatController.sendMessage` 等接口的 userId 由客户端请求参数传入，攻击者可以篡改 userId 访问其他用户的对话数据，存在越权（IDOR）风险。

**解决方案：** 服务端统一身份校验：
- Java 端通过 `SecurityContextHolder.getContext().getAuthentication().getName()` 从 JWT Token 中获取用户身份
- 不再信任客户端传入的 userId
- 所有涉及用户数据的接口统一校验

### 10.8 SSE 流式通信的 Android 端适配

**问题：** Android 端使用 OkHttp 接收 SSE 流式响应时，遇到多个问题：
- 连接超时设置不合理导致长回复被截断
- JSON 解析异常时整个流中断
- 错误事件和正常结束事件的区分

**解决方案：**
- 将 `readTimeout` 从秒级改为 5 分钟，适配长回复场景
- 每个 SSE 事件独立 try-catch，单个事件解析失败不影响整体流
- 通过事件类型字段（`end` / `error`）明确区分正常结束和异常

### 10.9 键盘弹起遮挡输入框

**问题：** Android 对话页点击输入框弹起键盘时，输入框被键盘遮挡，或输入框与键盘之间出现空白间隙。

**解决方案：**
- `AndroidManifest.xml` 中配置 `android:windowSoftInputMode="adjustResize"`
- Compose 层使用 `imePadding()` 处理 IME 避让
- 移除外层 Column 的 `windowInsetsPadding(WindowInsets.navigationBars)` 避免双重 padding

## 11. 项目创新点

### 11.1 从"看广告"到"对话购物"——交互范式转变

**传统模式局限：** 静态图文/短视频，单向"看与被看"，用户只能被动浏览。

**本项目方案：** 用户通过自然语言对话表达需求，AI 理解意图后主动推荐。

```
传统模式：用户浏览 → 看到商品 → 自行判断 → 决定购买
本项目：  用户说"推荐一款适合油皮的洗面奶" → AI 理解肤质需求 → 检索匹配 → 生成个性化推荐话术 + 商品卡片
```

这不是简单的"搜索框"，而是真正的**对话式导购**——AI 能理解模糊需求、追问细节、记住上下文，像一个懂商品的真人导购。

### 11.2 模糊需求理解——解决"用户说不清"的痛点

**传统模式局限：** 用户产生模糊兴趣时无法深度互动。比如用户想买"一个不贵又好用的耳机"，传统电商只能靠关键词匹配，结果要么太多要么不准。

**本项目方案：** LLM 理解模糊语义 + RAG 精准检索：

```
用户: "推荐一个不贵的耳机"
  → LLM 理解："不贵"= 价格敏感，"耳机"= 品类
  → RAG 检索：按价格升序 + 评分加权排序
  → 返回：性价比最高的几款 + 推荐理由
```

项目实现了**四级搜索流水线**（排除词提取 → 关键词提取 → 三级优先级匹配 → 参数化查询），能处理"跑鞋"（不拆字）、"不要优衣库"（反选排除）、"敏感肌用的"（肤质过滤）等复杂语义。

### 11.3 多模态交互——降低表达门槛

**传统模式局限：** 用户只能通过文字搜索或分类浏览找到商品，表达方式单一。

**本项目方案：** 支持文字、语音、拍照三种交互模态：

| 模态 | 场景 | 实现 |
|------|------|------|
| 文字 | 常规对话 | SSE 流式输出，逐字渲染 |
| 语音 | 不方便打字时 | MediaRecorder 录音 → 豆包多模态 ASR → 文字填入输入框 |
| 拍照 | 看到同款想找 | 拍照/选图 → 豆包 Vision API 理解图片 → 提取商品特征 → 搜索推荐 |

拍照识图不是简单的 OCR 文字提取，而是**语义理解**——拍一张街拍照片，AI 能识别出"白色Nike运动鞋"并搜索同款。

### 11.4 反选排除——精准过滤不需要的商品

**传统模式局限：** 传统电商筛选器是固定维度（价格/品牌/评分），无法表达"不要什么"。

**本项目方案：** 支持自然语言否定语义：

```
用户: "推荐防晒霜，但不要含酒精的"
  → LLM 提取排除词：["酒精"]
  → 检索时过滤：WHERE tags NOT LIKE '%酒精%'
  → 返回：不含酒精的防晒霜
```

这一能力在传统电商中很难实现——用户需要手动在筛选器中逐个排除，而在本项目中一句话就能完成。

### 11.5 渐进式需求收敛——多轮对话逐步精准

**传统模式局限：** 每次搜索都是独立的，用户需要反复调整关键词，之前的搜索意图不会被记住。

**本项目方案：** 多轮上下文记忆 + 渐进式过滤：

```
用户: "推荐跑鞋"
AI:   [推荐5款跑鞋]
用户: "要轻量的"
AI:   [从上一轮结果中筛选轻量款]  ← 不是重新搜索，而是在已有结果中过滤
用户: "不要超过五百"
AI:   [进一步按价格过滤]
```

Agent 通过会话记忆记住之前的推荐结果和用户偏好，每轮对话都在前一轮基础上进一步收敛，而不是从零开始。

### 11.6 对话式购物车管理——自然语言替代手动操作

**传统模式局限：** 购物车管理需要手动点击"加入购物车"按钮、勾选删除等机械操作。

**本项目方案：** 通过自然语言指令管理购物车：

```
用户: "把这个加到购物车"        → Agent 识别商品 → 执行加购
用户: "删除第二个商品"          → Agent 解析"第二个" → 定位商品 → 确认卡片
用户: "清空购物车"              → Agent 批量操作 → 确认卡片
```

Agent 需要维护对话上下文中的商品列表状态，理解"这个"、"第二个"等指代词，并通过确认卡片让用户在执行前确认，避免误操作。

### 11.7 三层防幻觉机制——确保推荐可信

**传统模式局限：** 传统电商的商品信息来自数据库，不存在"编造"问题。但 AI 推荐系统的核心风险就是 LLM 幻觉——编造不存在的商品、虚高的评分、错误的价格。

**本项目方案：** 三层防幻觉保障：

| 层级 | 机制 | 作用 |
|------|------|------|
| Prompt 约束 | 明确指令"不要编造" | 从源头减少幻觉概率 |
| 输出校验 | `validateProductCards()` | 用 product_id 查数据库比对，不一致则用真实数据覆盖 |
| 参数化查询 | SQL 注入修复 | 防止恶意输入篡改查询逻辑 |

最终效果：推荐的商品一定存在于数据库中，价格、评分、库存等信息与数据库一致。

### 11.8 五层可编排 Agent 架构——兼顾效率与能力

**传统模式局限：** 单一 LLM 调用无法处理复杂的多步推理任务；但所有请求都走完整编排又会增加简单请求的延迟。

**本项目方案：** 分层路由，按复杂度选择执行路径：

| 复杂度 | 路径 | 示例 | 延迟 |
|--------|------|------|------|
| 简单 | RouterAgent → 子 Agent 直接返回 | "推荐跑鞋" / "你好" | ~2s |
| 中等 | RouterAgent → 子 Agent → Tool 调用 | "这款手机参数是什么" | ~4s |
| 复杂 | RouterAgent → Orchestrator → Planner → Executor | 多步知识问答 | ~8s |

简单请求走最短路径快速响应，复杂请求走完整编排保证错误重试、状态追踪、事件监控。这比"所有请求都走编排"或"所有请求都直接调用 LLM"都更合理。
